## Context

FusionCanvas currently has three independently maintained representations of UI intent: documentation images generated by Python, an interactive HTML mockup, and production Avalonia AXAML. Even a high-quality wireframe leaves layout defaults and component semantics implicit, allowing an AI or human implementer to reinterpret the design during conversion.

This module is a developer-tooling spike. It uses two user-approved Issue #185 wireframes recovered from the exploration thread: `catalog-mockups-variants-wireframe-v1.png` and `catalog-mockups-design-areas-wireframe-v2.png`. Variant Management exercises vertically ordered regions, peer choice cards, dividers, command alignment, and a structured table. Design Areas exercises a collection-plus-focused-editor master-detail composition, repeated summary cards, form controls, supporting measurements, and action placement. Together they test whether one vocabulary preserves two distinct composition families. The reference images are design evidence; production views remain unchanged.

The stakeholders are FusionCanvas contributors and AI coding agents that need a less ambiguous handoff between design intent, wireframes, and future Avalonia implementation. There is no end-user workflow, persistent application data, migration, or live desktop requirement in this module. UX preflight is therefore not applicable.

## Goals / Non-Goals

**Goals:**

- Establish a small, explicit, versioned UI description vocabulary based on demonstrated FusionCanvas needs.
- Parse and validate descriptions with stable, actionable diagnostics.
- Convert a validated description and named state into a deterministic standalone SVG wireframe.
- Prove the vocabulary against two approved wireframes with complementary composition and narrow alternate-state projections.
- Keep the intermediate semantic model independent from both SVG and Avalonia so later renderers can be evaluated without redefining the language.
- Produce enough tests and documentation to decide whether a later AXAML-generation module is warranted.

**Non-Goals:**

- Generate or load production AXAML.
- Generate view models, bindings, commands, persistence, or business behavior.
- Replace or modify the production Variant Management or Design Areas views.
- Reproduce Avalonia font measurement or native rendering pixel-for-pixel.
- Support arbitrary Avalonia controls, custom controls, arbitrary styling, free-form expressions, animations, responsive breakpoints, accessibility trees, or asset embedding.
- Create a graphical authoring tool or migrate screens beyond the two approved fixtures.
- Establish the prototype format as a public plugin API or promise backward compatibility beyond explicit schema-version rejection.

## Decisions

### Use YAML as the authoring syntax and a strict validated semantic model as the contract

The checked-in source will use `.ui.yaml` with `schemaVersion: 1`. YAML is concise enough for humans and AI agents to author while preserving lists and hierarchy naturally. A maintained YAML parser will deserialize into syntax DTOs with strict unknown-property handling. A separate semantic validator will produce an immutable validated model consumed by layout and rendering.

The implementation may add a narrowly scoped `YamlDotNet` dependency to the tooling project after checking its license and vulnerability status. Writing a custom YAML parser is prohibited because parser edge cases are unrelated to the question the spike is intended to answer.

Alternatives considered:

- JSON avoids a dependency but is noisy for nested authoring and discourages readable examples.
- A custom indentation language looks attractive but would spend the spike on parsing and escaping rules before the vocabulary has been proven.
- Treating YAML as an unvalidated prompt would remain nondeterministic and would not solve the handoff problem.

### Keep the prototype outside production architecture layers

Create a repository-local .NET console project under `tools/FusionCanvas.UiDescription` and a matching xUnit project under `tests/FusionCanvas.UiDescription.Tests`, both included in `FusionCanvas.sln` so the normal baseline executes their tests. The tool must not reference `FusionCanvas.App`, `FusionCanvas.Application`, `FusionCanvas.Domain`, or `FusionCanvas.Integration`; it models design descriptions, not product behavior. Production projects must not reference the tool.

Likely responsibilities are:

- `Parsing/UiDescriptionParser`: YAML decoding and syntax-location capture.
- `Model/*`: syntax DTOs and the immutable validated semantic model.
- `Validation/UiDescriptionValidator` and `UiDiagnostic`: semantic rules and stable diagnostics.
- `Layout/UiLayoutEngine`: deterministic measure-and-arrange behavior.
- `Rendering/SvgWireframeRenderer`: canonical SVG serialization.
- `Commands/ValidateCommand` and `RenderCommand`: argument validation, diagnostics, exit behavior, and atomic output replacement.

This keeps experimental tooling out of Clean Architecture layers while still making it warning-clean and routinely tested.

### Start with a closed vocabulary derived from the fixture

Schema version 1 supports only the demonstrated vocabulary:

- Containers: `stack`, `grid`, and `panel`.
- Leaves: `text`, `field`, `select`, `list`, `table`, `button`, `message`, and `divider`.
- Semantic variants needed by the fixtures, such as screen and section headings, supporting and muted text, standard and elevated panels, summary and choice cards, single-line and multiline fields, primary, secondary, destructive and list-item buttons, empty/error/warning/danger messages, structured tables, dividers, and horizontal action groups.
- Layout values: `content`, `fill`, or a non-negative finite fixed number in device-independent units; explicit viewport size; named spacing and padding tokens; start, center, end, and stretch alignment; grid row and column placement; and controlled minimum sizes where the fixture demonstrates them.

Unknown node kinds, variants, tokens, properties, and incompatible combinations are errors. The renderer has no permissive fallback because silent defaults recreate the original ambiguity.

Absolute child coordinates are intentionally absent. The SVG contains coordinates only as the computed result of layout.

### Separate semantic tokens from raw visual values

The source references a renderer-owned `fusioncanvas-wireframe-v1` token profile rather than restating colors, fonts, corner radii, and common gaps on every component. The profile provides deterministic wireframe metrics and neutral styling corresponding to the intent of `docs/ui-guidelines.md`; it is not the production Avalonia theme.

Version 1 permits fixed numbers only where layout structure genuinely requires them, such as viewport dimensions, the Design Areas collection width, and deliberate minimum heights. Repeated visual decisions use named tokens. This distinction lets later work map the same semantic intent to Avalonia resources without asserting that SVG values are production pixels.

### Use narrow named-state overrides instead of an expression language

The base hierarchy describes component identity and structure. Each named state may override only:

- `visible` for any component;
- `enabled` for interactive leaves;
- literal `text` for text-bearing leaves; and
- representative `items` for list components and `rows` for table components.

Overrides target stable component IDs. They cannot create, remove, reparent, reorder, or change the kind or variant of nodes. This is enough to demonstrate a provider-unavailable or empty-collection projection without inventing data binding or boolean-expression semantics.

A simplified shape is:

```yaml
schemaVersion: 1
tokenProfile: fusioncanvas-wireframe-v1
screen:
  id: manage-variants
  title: Catalog & Mockups - Manage Variants
  viewport: { width: 1200, height: 820 }
  root:
    id: canvas
    kind: stack
    gap: section
    children:
      - { id: title, kind: text, variant: screen-heading, text: Catalog & Mockups - Manage Variants }
      - id: workspace
        kind: panel
        variant: elevated
        children:
          - { id: available-heading, kind: text, variant: section-heading, text: 1. Available choices }
          - id: choice-cards
            kind: grid
            columns: [fill, fill]
            gap: region
            children: []
          - { id: section-divider, kind: divider }
          - { id: variants-heading, kind: text, variant: section-heading, text: 2. Sellable variants }
          - { id: variants-table, kind: table, variant: data-table, columns: [Color, Size, Provider SKU, Available, Actions], rows: [] }
states:
  default: { overrides: {} }
```

The complete fixtures will include the full hierarchies and required states. YAML authoring order determines child order but not diagnostic or SVG attribute order.

### Make layout deterministic rather than platform-faithful

`UiLayoutEngine` performs deterministic measure and arrange passes using only the validated model and renderer-owned metrics:

1. Resolve the explicit viewport and outer padding.
2. Measure content-sized leaves with fixed component metrics. Text-dependent widths use a documented invariant approximation based on Unicode scalar count and variant metrics, never operating-system font measurement.
3. Allocate fixed and content tracks, subtract gaps, and distribute remaining space to `fill` tracks. More than one fill track shares remaining space equally in version 1.
4. Arrange stack or grid children in source order with deterministic rounding.
5. Apply clipping at the viewport and fail layout when required minimums cannot be satisfied; do not silently overlap or resize below minimums.

The algorithm uses invariant culture and finite decimal arithmetic or explicitly rounded floating-point values. Layout errors identify the responsible container and constraint.

Alternatives considered:

- Hosting Avalonia headlessly would make the prototype dependent on production framework behavior and blur the boundary between wireframe semantics and AXAML generation.
- Browser layout would introduce browser and font variability and would no longer prove a repository-local deterministic transformation.

### Emit canonical, self-contained SVG

The SVG renderer writes UTF-8 without a byte-order mark, LF line endings, invariant numbers, a stable declaration and attribute order, and elements in semantic tree order. It writes no timestamp, generator machine path, random identifier, script, external stylesheet, external font, or linked asset. Every rendered component group includes a stable `data-ui-id` so tests and reviewers can relate output to the source.

`render` builds the entire output in memory, validates that serialization succeeded, writes a temporary file beside the destination, and atomically replaces or moves it into place. On failure it removes only its own temporary file and leaves an existing destination unchanged.

Identical source bytes are not required when two YAML documents are semantically equivalent; the guarantee is that the same validated description, state, viewport, and tool version produce byte-identical SVG.

### Provide a deliberately small command surface

The supported commands are:

```powershell
dotnet run --project .\tools\FusionCanvas.UiDescription -- validate <source.ui.yaml>
dotnet run --project .\tools\FusionCanvas.UiDescription -- render <source.ui.yaml> --state <name> --output <wireframe.svg>
```

Successful commands return `0`. Invalid arguments, source, semantics, state, or layout return a documented nonzero validation/usage code; unexpected I/O failures return a distinct documented nonzero operational code. Diagnostics go to standard error in stable source order and include a stable code, severity, source path, line and column when known, component or state identity when relevant, and a concise message. Successful validation does not rewrite source. Rendering requires an explicit state and output path.

## Risks / Trade-offs

- [The vocabulary overfits one layout family] -> Require both the ordered-region/table Variant fixture and the master-detail Design Areas fixture to validate through the same semantic model and renderer.
- [A deterministic SVG is mistaken for Avalonia fidelity] -> Document that the renderer proves structure and constraints, not native control metrics or pixel parity; do not reference Avalonia packages in the tool.
- [YAML flexibility creates ambiguous inputs] -> Reject aliases, custom tags, duplicate mapping keys, implicit type surprises, unknown properties, and non-finite numeric values; normalize line endings before parsing diagnostics.
- [Content-sized text varies across machines] -> Use renderer-owned invariant approximation metrics and embed no external fonts.
- [Golden files become brittle] -> Keep two focused fixtures with few meaningful states, pair byte comparisons with semantic structural assertions and side-by-side visual review, and regenerate only through the documented command.
- [The tool becomes speculative infrastructure] -> Stop at one format version, one renderer, and two evidence-selected fixtures; evaluate the module before proposing AXAML generation or additional screens.
- [Atomic replacement behaves differently across platforms] -> Implement same-directory temporary output and tested replace-or-move behavior without weakening the guarantee that failures preserve an existing destination.

## Migration Plan

There is no application data or user migration. Add the tooling and examples without changing production projects. Rollback consists of removing the tool project, its test project, documentation, and generated fixtures; no production files require restoration. Schema version 1 is experimental, and unsupported versions fail explicitly rather than being migrated implicitly.

## Implementation Plan

1. Add `tools/FusionCanvas.UiDescription/FusionCanvas.UiDescription.csproj` as a warning-clean .NET console application and `tests/FusionCanvas.UiDescription.Tests/FusionCanvas.UiDescription.Tests.csproj` as its xUnit v3 test project; add both to `FusionCanvas.sln`. The tool may reference the approved YAML parser; no production project references change.
2. Add strict syntax DTOs and `UiDescriptionParser`. Configure parsing to reject unknown properties, duplicate keys, aliases, custom tags, malformed scalar types, and unsupported document multiplicity. Preserve source locations for diagnostics where the parser exposes them.
3. Add immutable semantic model types, the closed token/component registries, `UiDescriptionValidator`, and stable diagnostic codes. Validate version, root count, unique IDs, container/leaf composition, grid placement, sizing, token and variant compatibility, state names, targets, and allowed override properties before layout.
4. Add `UiLayoutEngine` with explicit viewport handling, content/fixed/fill measurement, stack and grid arrangement, deterministic metrics and rounding, minimum-constraint failures, and viewport containment checks. Keep layout types renderer-neutral.
5. Add `SvgWireframeRenderer` and canonical serializer. Emit semantic groups with `data-ui-id`, neutral token-profile styling, escaped literal content, representative list rows, enabled/disabled presentation, visibility filtering, and no external dependencies or nondeterministic metadata.
6. Add command parsing and the `validate` and `render` handlers. Define documented exit codes, standard-error diagnostics, explicit state selection, same-directory temporary output, atomic destination update, and cleanup limited to tool-created temporary files.
7. Preserve the approved source images under `docs/Visuals/ui-descriptions/references/`. Add `manage-variants.ui.yaml` and `manage-design-areas.ui.yaml` containing their complete fixture hierarchies and declared states. Render and check in one SVG per required state under the same folder. Add `docs/ui-description-language.md` describing vocabulary, exact sizing and state rules, commands, diagnostic shape, generation and comparison workflow, limitations, and the explicit non-AXAML boundary.
8. Add focused tests under `tests/FusionCanvas.UiDescription.Tests` for parser strictness, validation rules, deterministic diagnostic ordering, state override restrictions, layout allocation and containment, XML escaping, byte-identical repeated rendering, fixture structural markers, golden outputs, CLI exit behavior, and preservation of existing output on failure.
9. Run focused tool tests, the solution baseline, strict OpenSpec validation, and a changed-scope review proving no production UI or architecture layer changed. Populate `verification.md` with criterion-level results during implementation.

Decisions not to reopen during implementation: the fixtures remain the approved Issue #185 Variant Management v1 and Design Areas v2 wireframes; version 1 uses YAML; SVG is the only renderer; the tool remains independent of Avalonia and production layers; state overrides remain narrow; absolute child positioning, free-form expressions, AXAML generation, runtime loading, and additional screen migration remain out of scope. If either fixture cannot be represented without relaxing one of these constraints, implementation must stop and return the ambiguity for design review.

| --- | --- |
| Supported description is loaded | Parser tests using both checked-in fixtures. |
| Unsupported schema version is supplied | Parser or semantic-validation test asserting stable version diagnostic and no output. |

| Complementary wireframe hierarchies are described | Fixture semantic-tree assertions for ordered Variant regions/table and Design Areas master-detail regions. |
| Named layout tokens and variants are used | Fixture validation plus negative tests for unknown token and variant. |

| Duplicate component identifiers are supplied | Validation test asserting both locations. |
| Invalid component composition is supplied | Container/leaf and placement validation tests. |
| Invalid state override is supplied | State-target and property-compatibility tests. |
| Invalid source is validated repeatedly | Repeat-validation test comparing complete diagnostic records. |
| Named state is rendered | State projection test comparing identity, kinds, hierarchy, and allowed values before and after projection. |
| Unknown state is requested | Command/renderer test asserting diagnostic, nonzero exit, and no output. |
| Identical input is rendered repeatedly | Render twice into separate files and compare bytes. |
| Wireframe is inspected offline | XML test asserting self-contained SVG, `data-ui-id` markers, and absence of external/script references. |
| Fixed and flexible regions are arranged | Layout test asserting the declared Design Areas collection track, calculated editor bounds, and viewport containment. |
| Developer validates a valid description | CLI integration test asserting exit `0` and unchanged source bytes. |
| Developer renders a valid state | CLI integration test asserting exit `0` and expected SVG bytes. |
| Developer renders invalid input | CLI integration tests for validation and I/O failure, including unchanged existing destination. |
| Fixture outputs are reproduced | Golden-output tests for both default fixtures and narrow alternate states plus structural assertions. |

No Avalonia headless or live desktop test is planned because the module neither constructs nor changes an Avalonia view. `dotnet test .\FusionCanvas.sln` remains the required deterministic regression baseline.

## Open Questions

None for this module. Whether to generate AXAML, whether the vocabulary generalizes beyond these two screens, and whether descriptions should become a durable source of truth are evaluation questions for later discovery after this spike produces evidence; they are not delegated implementation decisions.
