## ADDED Requirements

### Requirement: Application version is generated from Git history
FusionCanvas SHALL derive the application version from the repository using Nerdbank.GitVersioning so that the same Git commit produces the same version whether it is built locally or in continuous integration.

#### Scenario: Contributor inspects the version configuration
- **WHEN** a contributor inspects the repository root
- **THEN** a `version.json` file exists and owns the manually maintained `Major.Minor` version
- **AND** a single central build dependency applies Nerdbank.GitVersioning to every Clean Architecture project rather than a per-project manual version

#### Scenario: Local build produces a version
- **WHEN** a contributor builds the solution from a clean local checkout
- **THEN** the built application assemblies carry a version whose `Major.Minor` matches `version.json`
- **AND** the `Build` component is generated automatically from Git version height

#### Scenario: Local and CI builds of the same commit agree
- **WHEN** the same Git commit is built locally and in GitHub Actions
- **THEN** both builds report the same product version and the same short commit identifier
- **AND** the canonical build number is derived from the repository, not from `github.run_number`

#### Scenario: CI checkout preserves full history
- **WHEN** FusionCanvas is built in GitHub Actions
- **THEN** the checkout configuration uses `fetch-depth: 0` or an equivalent that preserves the Git history Nerdbank.GitVersioning requires
- **AND** the contributor documentation states this requirement

#### Scenario: No project carries a conflicting manual version
- **WHEN** a contributor inspects the layer project files
- **THEN** no project sets a manually maintained `Version`, `VersionPrefix`, `PackageVersion`, or `AssemblyVersion` property that competes with Nerdbank.GitVersioning

### Requirement: Application exposes version information through a service
FusionCanvas SHALL expose application version information through an application-level port so views and view models never read assembly metadata directly.

#### Scenario: Application code requests the current version
- **WHEN** application code needs the current product version
- **THEN** it obtains an `ApplicationVersionInfo` value from an `IApplicationVersionProvider`
- **AND** the value carries a user-facing product version, the full informational version, and a short Git commit identifier

#### Scenario: Informational version is parsed consistently
- **WHEN** the informational version string has the form `Major.Minor.Build+g<commit>`
- **THEN** the product version is the substring before the `+`
- **AND** the short commit identifier is the substring after the `+` with the Nerdbank.GitVersioning `g` prefix removed
- **WHEN** the informational version string has no `+` metadata
- **THEN** the product version is the whole informational version
- **AND** the short commit identifier is reported as unknown

#### Scenario: Version provider reads generated assembly metadata
- **WHEN** the production version provider is constructed
- **THEN** it reads the informational version generated by Nerdbank.GitVersioning from application assembly metadata
- **AND** it does not depend on a hard-coded version string

### Requirement: Version and diagnostics are visible and copyable
FusionCanvas SHALL present the product version in a discoverable settings surface and SHALL expose a copyable diagnostic block suitable for bug reports.

#### Scenario: User opens the About surface
- **WHEN** the user opens Settings and selects the About section
- **THEN** the surface shows the FusionCanvas product name and a user-friendly product version of the form `Version Major.Minor.Build`
- **AND** the long informational version is not shown as the primary user-facing version when it is unnecessarily long

#### Scenario: User copies diagnostic information
- **WHEN** the user activates the copy action in the About surface
- **THEN** the clipboard receives a diagnostic block containing the product version, the short commit identifier, and the runtime platform
- **AND** the diagnostic block is formatted as plain text that can be pasted directly into a bug report

#### Scenario: Commit is unavailable
- **WHEN** the version provider cannot determine a commit identifier
- **THEN** the About surface and the copied diagnostic block report the commit as unknown rather than displaying a stale or empty value

### Requirement: Release tag convention is documented
FusionCanvas SHALL document a release tag convention that keeps the Git tag, application version, release title, and artifact filename aligned.

#### Scenario: Contributor creates a release
- **WHEN** a contributor documents or performs a release
- **THEN** the convention states the Git tag form `vMajor.Minor.Build`
- **AND** the convention notes that the application version, release title, and artifact filename use the same `Major.Minor.Build` value
