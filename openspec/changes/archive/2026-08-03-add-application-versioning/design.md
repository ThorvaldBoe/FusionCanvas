## Context

FusionCanvas ships no versioning today. The layer `.csproj` files set no `Version`, `VersionPrefix`, `PackageVersion`, or `AssemblyVersion` properties, so each assembly falls back to the .NET default `1.0.0.0` and the running application cannot tell the user which build it is, cannot be traced to a Git commit, and cannot keep a local build and a future GitHub Actions build of the same commit in sync.

The application already has a focused Settings window with a section rail (`General`, `AI`, `Workspace`) and a `SettingsSection` enum that controls which pane is visible. `SettingsViewModel` is constructed by `AppServicesFactory.Create()` for the production desktop path and by `MainWindowViewModel.CreateSettings` for offline/test paths. The Settings surface is the lowest-risk place to expose version information without introducing a new top-level window or dialog.

Nerdbank.GitVersioning (NB.GV) is the versioning mechanism requested by the issue. It owns `Major.Minor` in a `version.json`, derives the `Build` component from Git version height, stamps the informational version as `Major.Minor.Build+g<commit>`, and writes assembly metadata at build time. The same commit always yields the same version locally and in CI when the checkout preserves full history.

## Goals / Non-Goals

**Goals:**

- Derive `Major.Minor.Build` from the repository so local and CI builds of the same commit agree.
- Keep the manually maintained `Major.Minor` in one repository-root file and the NB.GV dependency in one central build file.
- Expose version information through an Application-layer port so views and view models never read assembly metadata directly.
- Show a user-friendly `Version Major.Minor.Build` in a discoverable surface and let the user copy a diagnostic block (version, short commit, platform) for bug reports.
- Keep the parsing, formatting, and copy-command behavior testable at the lowest reliable layer without depending on a live Git checkout at test time.
- Build successfully in Debug and Release with no manually maintained version conflicts.

**Non-Goals:**

- Creating a separate About dialog window; the About section lives inside the existing Settings window.
- Implementing a GitHub Actions release workflow, artifact publishing, or auto-update channels.
- Plugin or premium-module version compatibility rules, changelog generation, or installer behavior.
- Surfacing the version on the splash screen or in the main shell header.
- Central Package Management for the whole repository; only the NB.GV dependency is centralized.

## Decisions

### D1: Central NB.GV dependency through `Directory.Build.props`

Add a single repository-root `Directory.Build.props` containing one `PackageReference` for `Nerdbank.GitVersioning`. MSBuild imports `Directory.Build.props` into every project under the repository, so all four Clean Architecture projects and the four test projects receive version-stamped assembly metadata from one declaration rather than seven duplicate `<PackageReference>` entries.

Alternative considered: add the package only to `FusionCanvas.App`. Rejected because the issue explicitly asks for central configuration where practical, and a single `Directory.Build.props` is the most central practical option without adopting full Central Package Management.

Alternative considered: enable Central Package Management with a `Directory.Packages.props`. Rejected as out of scope; it would force every existing package reference to move and is not required to centralize a single build-time dependency.

### D2: Repository-root `version.json` owns `Major.Minor`

`version.json` at the repository root sets `"version": "0.1"`, defines the release branch/tag ref specs, and enables cloud-build build-number integration. NB.GV searches upward from each project to find this file, so all projects share one source of truth. The initial `0.1` matches the issue's own example and the current early-development milestone; the `Build` component is generated automatically and is not stored.

### D3: Application-layer port, App-layer adapter

Place `ApplicationVersionInfo`, `IApplicationVersionProvider`, and the pure parsing/formatting helpers in `FusionCanvas.Application/Versioning/`. The concrete `AssemblyApplicationVersionProvider` lives in `FusionCanvas.App/Versioning/` and reads `AssemblyInformationalVersionAttribute` from the application assembly. This mirrors the existing `AvaloniaApplicationThemeController` pattern (an App-owned adapter implementing an Application-facing contract) and keeps assembly-metadata reflection out of views, view models, and the Application layer.

The provider reads the informational version string generated by NB.GV and delegates parsing to a pure helper so the parsing behavior is unit-testable without a real assembly.

### D4: Pure informational-version parsing and diagnostic formatting

A pure static helper `ApplicationVersionDiagnostics` owns:

- `TryParse(string? informationalVersion, out ApplicationVersionInfo)`: splits on `+`; the left side is the product version; the right side, with a leading `g` stripped, is the short commit id. Missing metadata reports the commit as `unknown`.
- `Format(ApplicationVersionInfo, string platform)`: produces the copyable block:
  ```
  Version: 0.1.42
  Commit: 3f91c2a
  Platform: Windows x64
  ```
- `BuildPlatformString()`: reads `RuntimeInformation` to produce the platform string at runtime.

The pure `TryParse` and `Format` functions are tested framework-free in `FusionCanvas.Application.Tests`. The provider and `BuildPlatformString` are covered by composition and view tests.

### D5: About section in the existing Settings window

Add `SettingsSection.About` to the enum, expose `IsAboutSection`, and add the `About` entry to the existing `Sections` list so the rail renders it. The About pane shows the product name, a user-friendly `Version {ProductVersion}` line, and a `Copy diagnostics` button bound to a `CopyDiagnosticsCommand`. The long informational version is not shown as the primary user-facing version.

Alternative considered: a separate About dialog/window. Rejected for this module because the Settings window already provides a focused, sectioned, keyboard-reachable surface and the issue explicitly allows a Settings page as the alternative location.

### D6: Clipboard abstraction for testability

Introduce `IClipboardService` in `FusionCanvas.App/Versioning/` with `SetTextAsync(string)`. The production `AvaloniaClipboardService` wraps `Application.Current.Clipboard` lazily and silently no-ops when the clipboard is unavailable (headless or no main window). `SettingsViewModel` receives the version provider and clipboard service as optional constructor parameters so existing offline/test construction sites keep working; production `AppServicesFactory` supplies the real implementations.

### D7: Optional dependencies preserve existing construction sites

`SettingsViewModel`'s constructor already uses optional parameters for AI and other services. The version provider and clipboard service are added as trailing optional parameters that default to an `UnknownApplicationVersionProvider` (returns `ApplicationVersionInfo.Unknown`) and a no-op clipboard. This keeps the many existing test and offline construction sites compiling and behaving, while the production path supplies real implementations.

### D8: Documentation of CI checkout and tag convention

Add a focused "Versioning and releases" section to `CONTRIBUTING.md` stating: the `fetch-depth: 0` checkout requirement, that `github.run_number` is not the canonical build number, and the `vMajor.Minor.Build` tag convention with aligned release title and artifact filename. No new release workflow is created in this module.

## Risks / Trade-offs

- [Risk] A shallow CI checkout degrades the build number to `0.1.0`-style values. → Mitigation: central `version.json` with `cloudBuild.buildNumber.enabled`, documented `fetch-depth: 0` requirement, and a spec scenario asserting the documentation exists. NB.GV still builds successfully with shallow history; it just produces a less useful version.
- [Risk] NB.GV adds build time and requires the repository to be a Git repo. → Mitigation: the repository is already a Git repo; local and CI builds already run inside a checkout. The package is a build-time-only dependency.
- [Risk] Adding `Directory.Build.props` could change existing build behavior. → Mitigation: the file contains only the single `PackageReference` and no other properties; existing `.csproj` files are unchanged.
- [Risk] Headless view tests cannot reach the real clipboard. → Mitigation: the clipboard service is abstracted; tests use a fake. The production service no-ops when the clipboard is unavailable.
- [Risk] New optional constructor parameters change `SettingsViewModel` signatures used by many tests. → Mitigation: parameters are trailing and optional; existing call sites compile unchanged. A focused regression review confirms no call site accidentally drops the real provider in production.
- [Risk] The informational version format differs from `Major.Minor.Build+g<commit>` in some NB.GV configurations. → Mitigation: the parser handles missing `+` metadata and missing `g` prefix gracefully, reporting `unknown` for the commit.

## Migration Plan

No data, settings, schema, file-format, or workspace migration is required. Deployment is build-time only: add `Directory.Build.props`, `version.json`, the Application-layer versioning types, the App-layer provider/clipboard adapter, the Settings About section, tests, and the documentation. Rollback removes those files and reverts the `SettingsViewModel`/`SettingsWindow` changes; no persisted user state requires cleanup.

## Open Questions

None. The initial `Major.Minor` value (`0.1`), the About-in-Settings surface, the central `Directory.Build.props` dependency, and the `vMajor.Minor.Build` tag convention are all bounded by the issue and the existing application state.

## Implementation Plan

1. **Repository version configuration** — Add `version.json` at the repository root with `$schema`, `"version": "0.1"`, `publicReleaseRefSpec` for `main` and `vX.Y.Z` tags, and `cloudBuild.buildNumber.enabled`. Add `Directory.Build.props` at the repository root with a single `PackageReference` to the latest stable `Nerdbank.GitVersioning` (added through `dotnet add package` so the resolved version lands in the file). Confirm no `.csproj` sets a competing manual version property.

2. **Application versioning contract** — Add `src/FusionCanvas.Application/Versioning/ApplicationVersionInfo.cs` (record with `ProductVersion`, `InformationalVersion`, `CommitId`, plus an `Unknown` static and an `IsCommitKnown` helper), `IApplicationVersionProvider.cs` (`GetVersion()`), and `ApplicationVersionDiagnostics.cs` (pure `TryParse`, pure `Format`, runtime `BuildPlatformString`). One primary type per file per the architecture guideline.

3. **App-layer provider and clipboard** — Add `src/FusionCanvas.App/Versioning/AssemblyApplicationVersionProvider.cs` that reads `AssemblyInformationalVersionAttribute` from a supplied assembly (default `typeof(App).Assembly`) and delegates parsing to `ApplicationVersionDiagnostics`. Add `IClipboardService.cs`, `AvaloniaClipboardService.cs` (wraps `Application.Current.Clipboard`, no-ops when unavailable), and `NullClipboardService.cs` for the default offline/test path.

4. **Settings About surface** — Extend `SettingsSection` with `About`, add `IsAboutSection` and the `About` entry to `Sections`, and extend `SettingsViewModel` with `ApplicationVersionInfo Version`, `string DiagnosticsText` (built via `ApplicationVersionDiagnostics.Format`), and `CopyDiagnosticsCommand` (async, awaits `IClipboardService.SetTextAsync`). Add trailing optional `IApplicationVersionProvider?` and `IClipboardService?` constructor parameters defaulting to `UnknownApplicationVersionProvider.Instance` and `NullClipboardService.Instance`. Update `SettingsWindow.axaml` with the About pane (product name, `Version {Binding Version.ProductVersion}`, multiline read-only diagnostics preview, and the `Copy diagnostics` button).

5. **Production wiring** — In `AppServicesFactory.Create`, construct `AssemblyApplicationVersionProvider` and `AvaloniaClipboardService` and pass them to `SettingsViewModel`. The offline/test path in `MainWindowViewModel.CreateSettings` keeps the defaults.

6. **Framework-free tests** — In `tests/FusionCanvas.Application.Tests/Versioning/`, add `ApplicationVersionDiagnosticsTests.cs` covering: parsing `0.1.42+g3f91c2a` → product `0.1.42`, commit `3f91c2a`; parsing `0.1.42` → commit `unknown`; parsing empty/null → `Unknown`; `Format` produces the exact three-line block; `Format` reports `Commit: unknown` when missing. In `tests/FusionCanvas.App.Tests/Settings/`, extend `SettingsViewModelTests.cs` with a fake clipboard and assert `CopyDiagnosticsCommand` invokes the clipboard with the formatted block, and that the About section is selectable.

7. **Headless view test** — In `tests/FusionCanvas.App.Tests/Settings/SettingsWindowTests.cs`, add a test that constructs `SettingsWindow` with a `SettingsViewModel` carrying a known `ApplicationVersionInfo`, selects `About`, and asserts the product version `TextBlock` shows `Version 0.1.42` and the `Copy diagnostics` button is visible and bound.

8. **Documentation** — Add a "Versioning and releases" section to `CONTRIBUTING.md` documenting `fetch-depth: 0`, the non-canonical status of `github.run_number`, and the `vMajor.Minor.Build` tag convention with aligned release title and artifact filename.

9. **Verification** — Run `dotnet build .\FusionCanvas.sln` (Debug and Release), `dotnet test .\FusionCanvas.sln`, and `openspec validate add-application-versioning --strict`. Record criterion-level evidence in `verification.md` before completion.

### Decisions not to reopen

- The About surface is a Settings section, not a separate dialog.
- The NB.GV dependency is centralized via `Directory.Build.props`, not Central Package Management.
- The initial `Major.Minor` is `0.1`.
- The canonical build number comes from the repository, not `github.run_number`.
- Views and view models never read assembly metadata directly; the App-layer provider does.
