## Context

Issue #320 enables the three existing fulfillment strategies and adds Printify credentials only to Shopify + Printify. User clarification establishes separate credentials per Store. `FulfillmentStrategy` already defines stable values 0/1/2; `FulfillmentStrategyPolicy` currently permits Manual only. The Store Editor selector currently lives in Basic info, although the store-management spec describes fulfillment setup within Catalog & mockups. This change keeps the current selector location to avoid an unrelated relocation; reconcile that existing drift separately rather than silently changing the editor layout.

OpenRouter already uses ktsu.CredentialCache behind an Application port. Its implementation and active OpenSpec change are reference patterns, not authority to put Printify secrets into AI contracts. StoreManagementViewModel is large: add a focused credential child view model rather than embedding a second provider integration in it.

## Goals / Non-Goals

Goals: selectable stable strategies; isolated per-Store native keys; focused masked replacement; explicit safe verification; deterministic acceptance coverage. Non-goals and lifecycle boundaries are in proposal.md, including deferred native-entry cleanup and no Shopify implementation.

## Decisions

### Conceptual and functional design

Use the existing fulfillment selector and disclose credential controls below it only for Shopify + Printify. Display the exact labels from the issue. Semantic error color supplements readable text. Native reads have loading/error states and an explicit Retry; an unreadable credential is not a missing credential. An unsaved Store shows save-first guidance and no native operation. Archived Stores do not enable key operations. After a successful Verify, show a compact shop selector with `name (id)` entries; changing it saves the selected shop ID through the existing Store context save path.

All strategies can be saved offline. Selecting a strategy does not contact a provider. Credential absence marks configuration incomplete but does not block Store creation, saving, or local catalog work. Verify is a deliberate test of Printify authentication and shops-read permission only. No Shopify token, shop binding, synchronization, or publishing readiness is implied.

The owned dialog names the captured Store and uses masked entry with no reveal toggle or stored-key prefill. Trim outer whitespace; reject empty or embedded control-character values before native/HTTP use. Save is a separate immediate credential operation, explicitly explained in the dialog; cancelling a later Store draft does not roll back a saved credential. Key Save works offline. On success, clear draft references, close, refresh presence, and clear previous verification. Clearing managed string references limits lifetime; do not claim guaranteed memory zeroization.

New Store drafts must be saved first. A saved Store with a draft Shopify + Printify selection may add a key; Verify requires that strategy to have been saved first, with inline save-first guidance. This avoids issuing a marketplace request while the persisted strategy is Manual. Presence lookup is tied to explicit Printify setup rather than local catalog editing. Leaving a persisted Shopify + Printify strategy prompts during Store Save, before any Store fields are committed. Declining restores its strategy selection and retains other draft fields; confirming saves once through the existing service. Keep the key when changing strategy or archiving.

Dialog dismissal with a nonempty draft uses the existing discard-confirmation pattern. While native Save is executing, disable edit/save/dismissal until completion because cancellation cannot reliably undo a native write. Verification is cancellable on context change; use both cancellation and a context generation token to discard late results. The child view model captures workspace ID, Store ID, and credential/context generation before await. Marshal result publication to the UI thread and compare context before publishing.

### Storage and request boundaries

Add Application ports specific to Store Printify configuration, not a speculative generic secrets framework. The application service resolves and validates the active workspace/Store identity, saved strategy, and archive state before operations. Presence/save apply to persisted active Stores; Verify additionally requires persisted ShopifyPrintify. Do not expose retrieved secrets to App. Native reads happen inside the application verification use case and return only safe status to UI.

Use service `FusionCanvas` with a deterministic persona such as `printify-api-key/{workspaceId:D}/{storeId:D}`. Never use names or a global fallback. The provider token is account-wide, but this per-Store native entry remains deliberate duplication so each Store has an explicit setup and replacement workflow; identical tokens across Stores are valid. Inspect the installed credential library's backend behavior before reuse; require native secure storage on supported platforms and report unavailable if a platform/backend cannot satisfy it. Do not broaden or refactor the existing OpenRouter adapter. Native entries are machine/OS-user local; same identities restored on the same OS user can reconnect to an existing entry. Transfers to another machine carry no credentials. Deletion cleanup is deferred; UUID-based identity prevents new Stores inheriting stale entries.

Printify verification uses an injected, separately owned HttpClient with redirects disabled, fixed HTTPS origin, a per-request Authorization bearer header, application User-Agent, a 15-second linked timeout, and no automatic retry. GET `/v1/shops.json` requires shops-read access; accept a successful JSON array including `[]`, parse only shop ID and title, and return those options without retaining other account data. Bound the response to 1 MiB; reject unexpected/oversized content as a safe service response failure. Map 401 to invalid/expired, 403 to insufficient permission, 429 to rate-limited, network/timeout and 5xx to retryable failures, and other status/format failures to unexpected response. Never display raw response bodies, exception messages, or request headers.

Endpoint, scope, authentication and User-Agent source: [Printify API reference](https://developers.printify.com/), checked 2026-09-07. Timeout and response bounds are FusionCanvas design choices.

5. **App presentation.** Add `StorePrintifyCredentialsViewModel` under App/Stores and a small `PrintifyApiKeyWindow` with its own draft view model. Implement Store Save transition warning before the existing update call; all unchanged draft behavior remains intact. In StoreEditorWindow bind status, Add/Manage, Verify, Retry, shop selection, and busy/error states using compiled bindings and automation IDs. Adapt owned-dialog creation and focus in code-behind only. Verify is visible for an available key but disabled with save-first guidance when selected strategy differs from persisted strategy. Unsubscribe events and cancel pending work when windows/context close.
6. **Behavior and view coverage.** Extend `StoreManagementViewModelTests.cs` and `StoreEditorHeadlessTests.cs`, and add focused credential VM/dialog tests. Cover exact labels and visibility, three option labels, archive/draft guards, masked empty entry, keyboard focus and return, discard confirmation, save failure/retry, duplicate suppression, captured identity and late-completion rejection. Use controllable TaskCompletionSource fakes for races, not timing sleeps. Keep external accounts and native contributor credentials out of the baseline.
7. **Verification and delivery.** Populate every verification.md row with actual tests/evidence, run solution build/test and strict OpenSpec validation, inspect changed scope for security, architecture and accepted-spec drift, and record retrospective. Archive only after acceptance gates pass. Follow the repository issue completion workflow after successful apply/verification; never treat artifact completeness as implementation approval.

## Risks / Trade-offs

- Native backend behavior varies: inspect the existing library and fail closed when unavailable; baseline tests use injected stores. Optional isolated native smoke tests supplement the contract checks.
- Native credentials and SQLite are not transactional: new Store save occurs first and key save remains independent. No cross-store rollback or plaintext staging is introduced.
- Retained entries after deletion remain in the OS vault: explicitly defer cleanup rather than expanding this module into every workspace deletion/import path.
- Selecting Shopify strategies does not deliver Shopify integration: explain the current configuration-only scope near setup.
- App editor placement already differs from the accepted store-management spec: retain existing placement and record this pre-existing drift; do not claim the module corrected it.

## Migration Plan

No schema migration or numeric strategy changes. Existing Stores stay at their saved values; legacy Manual defaults remain. Existing OpenRouter credentials are untouched. Reverting application code hides the new UI but retains secure native entries; older code may reject updates to non-Manual Stores, so rollback is not represented as fully behavior-compatible.

## Open Questions and Approval

No unresolved implementation choices are delegated. The package proposes save-first behavior, no saved-key reveal, independent offline key Save, retained credentials, and deferred deletion cleanup. These details require delivery-package review before apply. User-confirmed strategy names and per-Store ownership must not be reopened.
